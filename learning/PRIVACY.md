# Learning Privacy Boundary

## Principle

The learning system must minimize data before anything can cross from a user project into a shared knowledge workflow.

## Default

**No public contribution by default.**

Project memory remains project-scoped.

## Safe learning evidence

Prefer:

- generalized technical observations
- anonymized counts
- reproducible test outcomes
- public/open-source references
- sanitized error classes
- abstracted architecture patterns
- regression-test results

## Unsafe learning evidence

Never export:

- API keys
- passwords
- access tokens
- connection strings containing secrets
- private source code
- private repositories
- proprietary datasets
- customer records
- personal data
- sensitive locations
- raw chat transcripts

## Minimization

Before a candidate is shared:

1. remove direct identifiers
2. remove unnecessary project details
3. remove secret-bearing fields
4. generalize proprietary terminology
5. retain only evidence needed to evaluate the claim
6. record the privacy decision

## Public repository rule

If a lesson cannot be expressed without exposing private or proprietary information, it should not be promoted to the public repository.

## Important distinction

Anonymized evidence is not automatically valid evidence.

Privacy review answers:

> "Is this safe to share?"

Validation answers:

> "Is this technically true and generalizable?"

Both are required.
